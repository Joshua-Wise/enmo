# 01 — Sign in with a username and password, and manage users

**What to build:**
The site asks for a username and password before showing anything: the Dashboard, Campuses, Incidents, History and Settings are all behind sign-in, and so is the API they read. Admins add, edit, disable and remove users on Settings. A fresh install has one user, `admin` with password `admin`. Asked for by the owner, 2026-10-08.

This reverses ADR 0003's "viewing the dashboard and history stays unauthenticated by design" and replaces pasting the Admin token in Settings with signing in. A new ADR records it and marks 0003's viewing clause superseded. The Device token is unchanged. `ADMIN_TOKEN` stays as the machine credential for the bench watcher, `deploy.sh`/`deploy.ps1` and `e2e/walk.mjs`, so none of them changes.

**Blocked by:** none

**Status:** done

**GitHub:** #38

- [x] Users in the database (a migration): username (unique, case-insensitive), password hash, role (`admin` or `viewer`), disabled flag, created and last-sign-in times. Passwords hashed with Node's `crypto.scrypt` and a per-user salt, compared in constant time; no new dependency
- [x] First start with no users creates `admin` / `admin` with role admin, and logs that it did (never the password of any other user)
- [x] Signing in with `admin` / `admin` (the default still in place) goes straight to a "Choose a new password" screen and nothing else until it is changed; the API refuses everything but that change for this session
- [x] `POST /api/session` (sign in), `DELETE /api/session` (sign out), `GET /api/session` (who am I). A session is a random id in an `HttpOnly`, `SameSite=Strict` cookie (`Secure` over https), stored server-side so sign-out and disabling a user end it at once. It expires after 12 h idle and 7 days at most
- [x] Sign-in failures say only "Wrong username or password", and are limited per address and per username (as the wrong-token limit is), so admin/admin cannot be guessed at speed
- [x] Every API route the pages read (`/api/dashboard`, the stream, History, Incidents, Campuses, Devices) needs a session; every change needs an admin session or the Admin token; `/api/readings`, `/api/firmware` (Device token) and `/api/health` stay as they are. The SSE stream is authorized by the cookie, and a session that ends closes it
- [x] Frontend: loading any page without a session shows a sign-in page, per DESIGN.md, and returns to the page asked for. A user menu shows who is signed in and has Sign out. The Admin-token box on Settings goes. Viewers see Settings' change controls hidden; the server refuses them anyway
- [x] Settings, Users tab (admins only): list users (role, disabled, last sign-in); add one with a username, role and starting password; reset a password; change a role; disable or delete. The last enabled admin cannot be demoted, disabled or deleted, and you cannot delete yourself
- [x] Every user can change their own password (current one required); at least 8 characters, except that it may not stay `admin`
- [x] `deploy.sh`/`deploy.ps1` gain `reset-admin-password` for a locked-out owner: sets a typed password (never echoed) on an admin, or recreates `admin` if none is left
- [x] Tests at the HTTP seam: no session → 401 on every read route and the stream; a viewer → 403 on every change; the Admin token still works for changes; the forced first change; sign-in limit; disabled user and sign-out end the session (stream included); the last-admin rules; cookie flags. Frontend: the sign-in redirect and return; the Users tab's refusals. `e2e/walk.mjs` signs in
- [x] README, DEPLOYMENT.md, the new ADR, CONTEXT.md (User, Admin, Viewer)

**Decisions (owner, 2026-10-08):**
- Two roles, Admin and Viewer.
- No kiosk exception: wall displays sign in like everyone else (7 days at most).
- `admin` / `admin` must be changed at first sign-in.

FOR UPDATE` on the enabled Admins; `ensureFirstUser` (called from `index.ts` after migrations) creates `admin`/`admin` with `must_change_password` and logs that line only. `sessions.ts`: cookie `ta_session` (`HttpOnly`, `SameSite=Strict`, `Path=/api`, `Max-Age` 7 days, `Secure` from `req.secure`), 12 h idle and 7 days at most, last-seen written at most once a minute; ending a session closes its streams (`sse.ts` now remembers which session opened each stream, `endStreams`, `streamSessions`); a sweep once a minute (`startSessionSweep`, stopped with the other jobs) forgets expired sessions, counts an open stream as use, and closes streams whose session ended some other way. `auth.ts`: `createAuth` gives `signedIn` (any session, or the Admin token) and `admin` (an Admin's session, or the Admin token); a session still on `admin`'s first password gets 403 "Choose a new password first"; a Viewer's change 403. `app.ts` puts `signedIn` in front of `/api/campuses`, `/api/devices`, `/api/dashboard` (stream included), `/api/incidents`, `/api/incidents.csv`, `/api/notifications`, `/api/system`, `/api/users`; every former `requireAdminToken` is now `auth.admin`; `/api/readings`, `/api/firmware`'s check and `/api/health` are untouched. **Decisions beyond the ticket.** The sign-in limit: failures only, 10 per username from any address and 30 per address, per 15 minutes, in memory; past either even the right password is refused (as the wrong-token limit), and a wrong current password on a password change counts against the user's limit. CSRF: `SameSite=Strict` plus every change made with the cookie must be `application/json` (the firmware upload `application/octet-stream`), else 415; sign-in reads only a JSON body (express.json), so no form can sign anyone in. The Admin token as a Bearer also passes every page read (so scripts can read), and `bench.py`/`demo.mjs` needed a one-line change each to send it on their reads, although the ticket said none of them changes. An open stream counts as use, so a wall display stays signed in to the 7-day cap. No one may disable themselves either (the ticket names delete). Signing in again from the same browser ends its previous session; changing your own password ends your other sessions; an Admin's new password for someone ends theirs. Only the first `admin` must change its password at first sign-in; users an Admin adds keep their starting password until they change it. Usernames are 1 to 64 of letters, digits, `. _ @ -`; passwords 8 to 200 characters. `reset-admin-password` also re-enables the user and makes it an Admin, and creates the named user whenever it is missing (not only when no Admin is left); a reset from the CLI closes that user's open streams at the next sweep (within a minute), not at once. Acknowledgement stays free text and is an Admin's change. Frontend: Viewers do not see the New devices, Firmware, Notifications, System or Users tabs (so they never ask for Admin-only reads); the Users tab does not offer resetting your own password (the user menu's Change password does, keeping your session); a first `GET /api/session` that fails other than 401 shows "The server did not answer" with Try again; the user menu is not modal (a Radix dialog opened from a modal menu left the page unclickable).
